# 데이터 무결성 가드 v2 (상시 자동 적용)

김보미 재정주권시민행동 플랫폼(김보미.com · 강진365 등)과 모든 데이터 작업에 무조건 적용한다.
사용자가 언급하지 않아도 기본 동작으로 삼고, 위반을 발견하면 지시 없이 즉시 수정한다.

> **v2 개정 사유 (2026-08-28).** v1은 "코드에 난수·해시가 있나"를 grep으로 훑는 데 그쳐,
> 난수가 아닌 형태의 허위 — 빈 API 응답인데 화면에는 "보유"라고 찍히는 배지, 페이지마다 다른
> 같은 지표, 근거 목록 없는 "N개" 단언, 24MB 이미지 — 를 전부 놓쳤다.
> 판정 근거를 **코드에서 렌더된 화면으로** 옮기기 위해 원칙 6~9와 반증 의무를 신설한다.

---

## 원칙 1 — 가짜 수치 생성 절대 금지

- 해시, 난수(`Math.random`, seed 난수), 플레이스홀더, "그럴듯한 추정치"로 통계값을 만들지 않는다.
- `rng(`, `hash01(`, `Math.random()*`, 임의 계수 곱셈으로 값을 만드는 코드는 발견 즉시 삭제 대상.
- 보간·추정이 꼭 필요하면 반드시 사용자에게 먼저 물어보고, 화면에 "추정"임을 명시할 때만 허용.

## 원칙 2 — 결측은 '데이터 없음'으로, 집계에서 제외

- 확보하지 못한 값은 null 유지 → 화면에는 '—' 또는 '데이터 없음'으로 표기한다.
- 결측 항목은 평균·합계·순위·등급 산출에서 제외한다(0으로 취급 금지).
- 구성 지표가 일부 결측이면 종합점수·등급 자체를 산출하지 않는다.

## 원칙 3 — 출처 표기 의무

수치가 표시되는 모든 화면·문서에 ①기관명 ②자료·API 코드 ③수집기간/기준시점 ④집계규칙을 함께 표기한다.
**산출범위도 출처의 일부다** — 같은 "잉여금"도 기금 포함 여부에 따라 값이 달라지므로
"일반회계+기타특별회계, 기금 제외" 같은 범위를 반드시 명시한다.

## 원칙 4 — 7단계 교차검증

1. **원천 대조** — 화면 값 vs 원본 API 재호출 값 1:1 (샘플 아닌 해당 범위 전건)
2. **결측 점검** — null이 '—' 표기·집계 제외로 이어지는지
3. **중복 점검** — 키 중복·이중 합산
4. **이상치 점검** — 비율 0~100, 음수 불가, 자릿수(억/원)
5. **표본 완전성** — 기대 행수(예: 243개 지자체) 충족, 미달이면 배포 중단
6. **정합성(항등식)** — 예산현액 = 지출+이월+잔액+불용 등 내부 산식 재계산
7. **해석 검증** — 외부 공시·보도 수치와 원 단위 교차 대조

## 원칙 5 — 하드코딩 금지·재개 가능한 수집

- 수치는 ①API 실시간 ②검증된 스냅샷 ③공시 상수 블록(출처 주석 필수) 중 하나로만 들어간다.
- 상수 블록은 생성 스크립트(API 호출 → 검증 → 출력)로 만들고, 중단 지점부터 재개 가능하게 작성한다.
- 배포 전 `node --check` 등 문법 전수 검증과 헤드리스 QA를 거친다.

# 신설 — 화면 기준 4대 검사 (매 작업 필수)

## 원칙 6 — 렌더된 화면값을 실 API 응답과 대조한다

**코드가 실데이터를 반환한다는 확인은 검증이 아니다.** 헤드리스 브라우저로 실제 렌더한 뒤,
사용자가 보는 텍스트·배지·라벨을 같은 시점의 API 응답과 1:1로 맞춘다.

- 상태 배지("보유", "연동됨", "실시간")가 **정적 문자열**이면 그 자체가 결함이다.
  배지는 반드시 응답에서 파생시키거나, 파생이 불가능하면 배지를 없앤다.
- **클릭 경로까지 검증한다.** "실데이터 보기 →" 같은 유도 문구가 있으면 실제로 눌러서
  값이 나오는지 확인한다. 목록 화면만 보고 통과시키지 않는다.
- API가 빈 응답이면 화면에 '데이터 없음'이 **보여야** 한다. 안 보이면 결함으로 기록한다.
- 대기 후에도 '로딩 중'이 남으면 결함이다. 늦게라도 풀리면 지연시간을 성능 결함으로 기록한다.

## 원칙 7 — 공유 수치는 전 페이지·전 사이트가 일치해야 한다

같은 지표가 두 곳 이상에 나오면 **반드시 값을 맞춘다.** 개별 검증만 하고 일관성 검증을 빼지 않는다.

- 지표별로 (라벨 → 값 → 페이지) 표를 만들어 서로 다른 값이 있는지 기계적으로 본다.
- 값이 다를 수밖에 없으면(산출범위 차이 등) **양쪽 화면에 범위를 명시**하고, 근거 데이터셋 코드를 밝힌다.
- 사이트가 여러 개면 사이트 간에도 대조한다(같은 지자체 지표가 A사이트·B사이트에 동시에 있는 경우).

## 원칙 8 — 모든 집계·홍보 문구는 실목록으로 검산한다

"N개 공약", "N건 수록", "N개 데이터셋", "N개 지자체" 같은 단언은 **난수가 아니어서 grep에 안 걸린다.**
따라서 별도로 검산한다.

- 화면 문구의 N ↔ 실제 DOM 목록 개수 또는 원천 자료(PDF 목차·API total)를 대조한다.
- 대조 대상이 사이트 밖(인쇄물 등)이면 **원문을 받아 실제로 세어** 확인하고, 근거를 화면에서 링크한다.
- 대조 불가한 단언은 화면에서 내린다.

## 원칙 9 — 성능예산을 지킨다

느려서 안 보이는 값은 없는 값과 같다.

- 페이지 총 전송량 **5MB**, 단일 자산 **1MB**, API 응답 **8초** 를 기본 예산으로 둔다.
- 초과 시 원인을 실측(자산별 바이트)해 보고한다. 이미지는 리사이즈·WebP·지연로딩으로 줄인다.
- 외부 위젯(유튜브·페북 등)은 통제 불가이므로 자사 자산과 분리해 집계한다.
- 외부 프록시를 폴백으로 줄줄이 시도하는 구조는 지연의 주범이므로 순서·타임아웃을 점검한다.

# 반증 의무 (확증편향 차단)

- **지목한 것 하나가 맞았다고 성공 보고하지 않는다.** 검사 범위를 스스로 좁히지 않았는지 먼저 되묻는다.
- 판정 전 **반대 가설을 한 번 검증한다.** "데이터가 없다"고 결론 내기 전에
  파라미터 조합·연도 전 범위·대체 엔드포인트를 모두 시도한다.
  (실제 사례: 연도 3개만 찔러보고 "18건은 상위 API에도 없음"이라 판정 → 표기연도 전 범위로 재검증하니 대부분 존재)
- **감사 도구 자체를 먼저 의심한다.** 도구가 만든 오탐을 사이트 결함으로 보고하지 않는다.
  (실제 사례: 프록시가 POST를 GET으로 바꿔 보내 `/api/track` 405를 사이트 버그로 오인)
  - 요청 프록시는 **메서드·헤더·본문을 반드시 보존**한다.
  - 셀렉터 기반 개수 검증은 대상 외 요소가 섞였는지 눈으로 확인한다.
  - 대기시간 부족으로 인한 '로딩 중' 오탐을 배제하도록 단계적으로 재측정한다.
- 오탐이었으면 **오탐이었다고 사용자에게 먼저 말한다.** 조용히 지우지 않는다.

# 완료 기준

아래를 모두 만족해야 "완료"라고 말한다.

1. 원칙 6~9의 4대 검사를 **실행한 로그·수치**가 있다 (주장 아님)
2. 발견 항목을 전부 시정했거나, 못 한 항목은 이유와 함께 남겼다
3. **배포 후 라이브에서 재확인**했다 (로컬 파일 확인만으로 끝내지 않는다)
4. 오탐이 있었다면 그 사실과 교정 내용을 함께 보고했다

# 실행 도구

`/home/claude/guard/audit4.js` + `sites.json` 이 원칙 6~9를 자동 수행한다.

```bash
node /home/claude/guard/audit4.js /home/claude/guard/sites.json
# HIGH 1건 이상이면 exit code 1 → 배포 차단 신호
```

새 사이트를 만들면 `sites.json`의 `sites[]`에 추가한다.
`clickProbes`(클릭 경로), `claims`(집계 문구), `sharedMetrics`(공유 수치)를 함께 등록해야
원칙 6·7·8이 그 사이트에도 적용된다.
